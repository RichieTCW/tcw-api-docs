TCW Partner API Guide

Read Trading Card World's live catalog and stock, order products and graded slabs for shipping, and, with a vaulting key, hold stock while you decide. It is a GraphQL API, and this page is everything you need to integrate.

Overview

Everything goes through one GraphQL endpoint with your API key. What your key can do depends on two things: its type and its scopes.

Key types

Every key is one of two types. Keys issued before November 2026 are vaulting keys. Ask us if you need the other type.

Direct order

You order, we ship.

  • Read the whole catalog, stock and the slab list
  • createOrder, including slabs
  • Store credit balance and top-ups
  • No holds and no vault slab purchases

Vaulting

Everything a direct-order key can do, plus:

  • Holds: keep stock aside while you decide
  • convertHold: ship a hold
  • requestSlabs: buy slabs that stay in TCW's vault

A call your key type doesn't allow fails with a FORBIDDEN error that names vaulting.

Scopes

Scopes switch on parts of the API. We set them when we issue your key.

scopelets you
catalog:readRead products, variants, prices, images and the stock band.
inventory:readSee the exact stock.quantity.
orders:readRead your own holds and orders.
orders:writePlace orders (createOrder, convertHold) and request store credit top-ups.
holds:writePlace, extend and release holds (vaulting keys).
slabs:readBrowse graded slabs and read your slab requests.
slabs:writeOrder slabs on createOrder, and on a vaulting key, buy them with requestSlabs.

A missing scope fails with a FORBIDDEN error that names the scope.

Quick start

endpoint
POST https://tcw-api-8rgfmmib.uc.gateway.dev/graphql
auth
Send x-api-key: <your key> on every request. We showed you your key once and don't store it, so we can't recover it. If you lose it, ask for a new one.
body
JSON {"query": "...", "variables": {...}}: standard GraphQL over HTTP. Simple reads also work as GET with a query parameter.
health
GET https://tcw-api-8rgfmmib.uc.gateway.dev/status needs no key and returns {"ok":true,"version":"..."}.
schema
Introspection is on. Point any GraphQL client at the endpoint with your key and it will autocomplete.

Your first call

curl -s https://tcw-api-8rgfmmib.uc.gateway.dev/graphql \
  -H "x-api-key: $TCW_API_KEY" -H "content-type: application/json" \
  -d '{"query":"{ variant(sku:\"PKMS-3246-N\"){ sku price stock{ band quantity checkedAt } product{ title } } }"}'
response
{"data":{"variant":{"sku":"PKMS-3246-N","price":"300.00",
  "stock":{"band":"IN_STOCK","quantity":4,"checkedAt":"2026-09-10T21:14:02Z"},
  "product":{"title":"Scarlet & Violet: Base Set - Booster Box"}}}}

Catalog and stock

The catalog is TCW's live, published products. Each condition or packaging of an item is its own variant, with its own SKU, price and stock.

What you can read

There are three entry points on Query:

fieldargumentsreturns
productsfirst (max 250), after cursor, query in Shopify search syntax, updatedSince ISO datetimeA page of products, most recently updated first.
productOne of id, handle, skuOne product, or null.
variantskuOne variant with its product, or null.

Product fields

id, handle, title, status, productType, vendor, tags, category (Shopify's standard taxonomy, when set), descriptionHtml, images, variants, url, createdAt, updatedAt, and card.

card holds clean details for trading cards: game, setName, setCode, cardNumber, rarity, edition, releaseDate, language, finishes and characters. It is null for other products.

Variant fields

id, sku, title, barcode, price (USD, as a string), compareAtPrice, availableForSale, stock and product.

Stock

fieldmeaning
quantityThe exact count available now (needs inventory:read). It can go negative if the shop oversold. Treat zero or less as none.
bandA summary of the same number: IN_STOCK above 3, LOW 1 to 3, OUT zero or less. Use quantity for anything that matters.
checkedAtWhen we read the figure, which is the moment of your request.

Stock is not a reservation. TCW sells in a store and online at the same time. quantity already excludes every hold and unshipped order, but it can be gone a minute later. Only an order or a hold takes stock off the shelf for you.

Inventory lookups

Every example here was run against the live API.

One SKU

{ variant(sku: "PKMS-3246-N") { sku price availableForSale stock { quantity checkedAt } } }
response
{"data":{"variant":{"sku":"PKMS-3246-N","price":"300.00","availableForSale":true,
  "stock":{"quantity":4,"checkedAt":"2026-09-10T15:52:17Z"}}}}

With a variable instead:

{"query": "query Stock($sku: String!) { variant(sku: $sku) { sku stock { quantity } } }",
 "variables": {"sku": "PKMS-3248-N"}}

Several SKUs in one request

Use aliases, up to 10 per request. This is the efficient way to check a short list.

{
  a: variant(sku: "PKMS-3246-N") { sku stock { quantity } }
  b: variant(sku: "PKMS-3311-N") { sku stock { quantity } }
  c: variant(sku: "PKMS-3248-N") { sku stock { quantity } }
}
response
{"data":{"a":{"sku":"PKMS-3246-N","stock":{"quantity":4}},
         "b":{"sku":"PKMS-3311-N","stock":{"quantity":1}},
         "c":{"sku":"PKMS-3248-N","stock":{"quantity":80}}}}

Every condition of one card

Singles have one variant per condition. Fetch the product to see them all:

{ product(handle: "espeon-deoxys-gx-sm240-sun-moon-black-star-promos") {
    title
    variants { sku title price stock { quantity } } } }
response (excerpt)
"variants":[{"sku":"SMP-SM240-EN-HF-1","title":"Near Mint Holofoil","stock":{"quantity":0}},
            {"sku":"SMP-SM240-EN-HF-2","title":"Lightly Played Holofoil","stock":{"quantity":0}},
            {"sku":"SMP-SM240-EN-HF-3","title":"Moderately Played Holofoil","stock":{"quantity":1}}, ...]

product(sku: "SMP-SM240-EN-HF-3") works too: give any one variant's SKU and you get the whole product. In single-card SKUs the suffix is the finish and condition: -NH-1 is Near Mint Holo, -HF-1 is Holofoil, and the last number is the condition tier.

By barcode (UPC)

{ products(first: 1, query: "barcode:820650853463") {
    edges { node { title variants { sku barcode stock { quantity } } } } } }

A SKU family by prefix

{ products(first: 250, query: "sku:PKMS-32*") {
    pageInfo { hasNextPage endCursor }
    edges { node { title variants { sku stock { quantity } } } } } }

Only what is in stock

{ products(first: 250, query: "inventory_total:>0 AND product_type:'Pokemon Sealed'") {
    pageInfo { hasNextPage endCursor }
    edges { node { title variants { sku price stock { quantity } } } } } }

inventory_total adds up all of a product's variants. A product with one condition in stock and four sold out still matches, so check each variant's quantity.

Search syntax

{ products(first: 50, query: "product_type:'Pokemon Sealed'") { edges { node { title } } } }
{ products(first: 50, query: "tag:'Prismatic Evolutions'") { edges { node { title } } } }
{ products(first: 50, query: "title:Charizard*") { edges { node { title } } } }

query takes Shopify's product search syntax: product_type:, tag:, vendor:, title: and sku:, combined with AND, OR and - (not). Terms match whole words, so add a trailing * for partial matches. Results are always limited to live, published products, whatever you pass.

Paging and syncing

Pull the whole catalog

query Page($after: String) {
  products(first: 250, after: $after) {
    pageInfo { hasNextPage endCursor }
    edges { node { id handle title productType tags
      variants { sku price compareAtPrice availableForSale stock { band quantity } } } }
  }
}

Loop while hasNextPage is true, passing endCursor as after. The catalog is a few thousand products, so a full pull is about 14 requests.

Fetch only what changed

{ products(first: 250, updatedSince: "2026-09-11T00:00:00Z") {
    pageInfo { hasNextPage endCursor }
    edges { node { id updatedAt variants { sku price stock { band quantity } } } } } }

Pass the time of your last successful sync. The most recent changes come first.

Ordering

One call places an order to ship anywhere you choose. Both key types can do it, and it can mix products and graded slabs.

How orders work

Orders are paid first. Your order is a request until it is paid. Nothing ships, and no Shopify order exists, before payment.

  1. You call createOrder. We set the stock aside and return a record with status REQUESTED, priced in full: subtotal, shipping, tax and total.
  2. You pay, either on the daily invoice or automatically from your store credit.
  3. Once paid, the status becomes PAID, then CONVERTED with a real order, usually within 15 minutes.
  4. We ship it. Follow order.fulfillmentStatus and order.tracking.

Price: items at TCW's retail price when you order, plus a flat $9.99 shipping per order, plus tax on both (none if your account is tax exempt).

The record createOrder returns is a Hold object. Keep its id: the order appears on it after payment.

Place an order

mutation {
  createOrder(input: {
    lines: [{ sku: "PKMS-1465-N", quantity: 1 }],
    shippingAddress: { firstName: "Sam", lastName: "Lee", address1: "1 Main St", city: "Dallas",
                       province: "TX", country: "US", zip: "75001" }
    reference: "PO-1044", idempotencyKey: "PO-1044-order" }) {
    hold { id status subtotal shipping tax total }
    order { name }
    problems { code message sku }
  }
}
response
{"data":{"createOrder":{"hold":{"id":"h_5b0e2a9c41f7","status":"REQUESTED","subtotal":"80.00",
  "shipping":"9.99","tax":"7.99","total":"97.98"},"order":null,"problems":[]}}}

Shipping address

Ship to yourself, or straight to your own customer. shippingAddress takes firstName, lastName, company, address1, address2, city, province, country, zip and phone. address1, city, country and zip are required. Check it before you send: you can't change it through the API afterwards.

email is optional and goes on the order. reference is yours, such as a PO or your customer's order number, and comes back on the record and the order.

Cancelling

You can't cancel through the API. Email us before it is paid and we'll cancel it. It then reads CANCELLED, with cancelledAt and cancelReason, and nothing is owed.

Order lines

Each line names one item in exactly one of three ways:

fielduse it for
skuMost products.
variantIdProducts with no SKU, mostly sports boxes and older sealed items. Use the Variant.id from the catalog; it never changes.
certA graded slab from the slab list. Quantity is always 1. Needs slabs:write.

You can mix all three in one order. Every line comes back with sku and variantId, and slab lines also with cert, so you can match on whichever you keep.

lines: [{ variantId: "44123456789012", quantity: 1 }, { sku: "PKMS-1465-N", quantity: 2 }]

Dry runs

Add dryRun: true to createOrder or createHold to price the lines and check for problems without writing anything. The real call takes the same input. A dry run prices the items only; shipping and tax are added when you place it for real.

mutation {
  createHold(input: { lines: [{ sku: "PKMS-1465-N", quantity: 1 }], holdDays: 1,
                      reference: "PO-1042", idempotencyKey: "PO-1042-hold", dryRun: true }) {
    hold { status units subtotal expiresAt lines { sku title unitPrice } }
    problems { code message sku }
  }
}
response
{"data":{"createHold":{"hold":{"status":"PREVIEW","units":1,"subtotal":"80.00",
  "expiresAt":"2026-09-19T16:25:45Z",
  "lines":[{"sku":"PKMS-1465-N","title":"Scarlet & Violet: Destined Rivals - Booster Bundle","unitPrice":"80.00"}]},
  "problems":[]}}}

Safe retries with idempotencyKey

Say you send an order, we place it, and the reply is lost on the way back. Your side sees a failure and retries. Without protection, that retry would place a second order and you'd be billed twice.

idempotencyKey prevents this. It is a label you choose for "this particular request", and it is required on createOrder, createHold, requestSlabs and requestTopUp. Something you already have works well, such as your PO number with a suffix: PO-1042-order.

  • Same key, same input: nothing new happens and you get back what the first call made. Retry as often as you like.
  • Same key, different input: refused with IDEMPOTENCY_MISMATCH, and nothing is written. Use a new key for a new request.
  • New key: a new request.

Keys only need to be unique within your own account. Create the key before you send, store it with the request, and reuse it on every retry. Calls that act on an existing record (convertHold, extendHold, releaseHold) don't need one: repeating them is always safe.

Track and list

{ hold(id: "h_5b0e2a9c41f7") { status order { id name paymentStatus fulfillmentStatus total } } }
{ order(id: "7087128739978") { name fulfillmentStatus tracking { number url company } } }
{ holds(status: REQUESTED) { id total expiresAt reference } }
{ orders(first: 20) { name createdAt total fulfillmentStatus reference } }

fulfillmentStatus goes from UNFULFILLED to FULFILLED, and tracking fills in when we ship. Polling every few minutes is fine. holds includes the records createOrder made; orders lists paid orders only. You only ever see your own.

Holds vaulting keys

A hold keeps specific units aside for you for a few days while you decide. While it stands, nobody else can buy them, in our store or online. You then ship it, release it, or let it expire.

Holds need a vaulting key with holds:write (and orders:write to ship them). Prices are fixed when the hold is placed. Graded slabs can't be held: order them instead.

Life of a hold

statusmeansmoves on when
HELDUnits kept for you until expiresAt.You ship, extend or release it, or it expires.
REQUESTEDYou asked for it to ship. Still kept for you; shipping, tax and total are set.You pay.
PAIDPaid; the order is being created.Automatic, usually within 15 minutes.
CONVERTEDThe order exists; read it from order.We ship it.
RELEASED / EXPIREDUnits back on sale.Final.
CANCELLEDWe cancelled the request before payment, for example at your request. Nothing is owed.Final.

createOrder records start at REQUESTED and follow the same path.

Place a hold

mutation {
  createHold(input: { lines: [{ sku: "PKMS-1465-N", quantity: 1 }], holdDays: 1,
                      reference: "PO-1042", idempotencyKey: "PO-1042-hold" }) {
    hold { id status units subtotal expiresAt }
    problems { code message sku }
  }
}
response
{"data":{"createHold":{"hold":{"id":"h_d79c13c62082","status":"HELD","units":1,"subtotal":"80.00",
  "currency":"USD","expiresAt":"2026-09-19T16:25:45Z","createdAt":"2026-09-18T16:25:45Z"},"problems":[]}}}

holdDays is 1 to 7 (default 3). Keep the id. From this moment the variant's stock.quantity is one lower for everyone, including you. Lines work exactly as for orders, except that slabs aren't allowed.

Request the shipment

convertHold turns a hold into an order request. It takes the same shipping address fields as createOrder, and is priced and paid the same way: $9.99 shipping per hold, plus tax.

mutation {
  convertHold(id: "h_d79c13c62082", input: {
    shippingAddress: { company: "Acme Cards", firstName: "Receiving", lastName: "Dept",
                       address1: "20 W 34th St", city: "New York", province: "NY", country: "US", zip: "10001" }
    reference: "PO-1042" }) {
    hold { status subtotal shipping tax total expiresAt }
    order { name }
    problems { code message }
  }
}
response
{"data":{"convertHold":{"hold":{"status":"REQUESTED","subtotal":"80.00","shipping":"9.99","tax":"7.99","total":"97.98",
  "expiresAt":"2026-09-25T16:28:40Z"},"order":null,"problems":[]}}}

The units stay kept for you until expiresAt. Pay before then, or they can sell elsewhere. Calling it again is safe and returns the hold as it is. Once requested, a hold can't be extended or released through the API; email us to cancel it.

Extend, release, expire

mutation { extendHold(id: "h_d79c13c62082", days: 2) { hold { expiresAt } problems { code message } } }
mutation { releaseHold(id: "h_d79c13c62082") { hold { status } problems { code message } } }
{ holds(status: HELD) { id units subtotal expiresAt reference } }
  • Extend: a hold can last 14 days in total, counting all extensions.
  • Release: gives the units back now. Safe to repeat.
  • Expire: a hold you do nothing with becomes EXPIRED at expiresAt and the units go back on sale. Place a new hold or order if you still want them.

Payment

Orders and shipped holds are paid one of two ways, depending on how your account is set up.

Daily invoice

We total your requests for each calendar day (US Eastern time) and invoice you. When the invoice is paid, each request becomes an order and ships. To see what is waiting, list holds(status: REQUESTED): the sum of a day's total is that day's invoice.

Store credit retainer

With a retainer, you keep a store credit balance with TCW and each order pays itself:

  • createOrder or convertHold takes its total from your balance straight away and goes to PAID. The order follows within about 15 minutes.
  • If the balance is too low, it waits in REQUESTED. Its paymentNote says how much is needed, and it pays itself (oldest first) as soon as a top-up arrives. Its stock stays kept for 7 days meanwhile.
{ storeCredit { balance pendingTopUps limit topUps { id status amount checkoutUrl expiresAt } } }

mutation {
  requestTopUp(input: { amount: "5000", reference: "November retainer", idempotencyKey: "4c1e2b7a-…" }) {
    topUp { id status amount checkoutUrl expiresAt }
    problems { code message }
  }
}
response
{"data":{"requestTopUp":{"topUp":{"id":"tu_3f9a0c2d71e4","status":"PENDING","amount":"5000.00",
  "checkoutUrl":"https://tradingcardworld.com/…/invoices/…","expiresAt":"2026-11-24T18:00:00Z"},"problems":[]}}}

Open checkoutUrl signed in as your company and pay by ACH or crypto. A top-up has no tax or shipping. It becomes CREDITED once the payment clears (ACH can take a few business days) and the amount is added to balance. Unpaid links expire after 7 days.

Your balance plus unpaid top-ups must stay under limit (10,000 USD); going over returns CREDIT_LIMIT. Without a retainer, storeCredit is null and requestTopUp returns STORE_CREDIT_NOT_SET_UP.

Graded slabs

Graded slabs are single graded cards in TCW's vault. Each is one of a kind, so you name it by its cert number. You can order slabs shipped to you, or, with a vaulting key, buy them to keep in our vault.

Browse

Needs slabs:read. Works with either key type.

{
  slabs(first: 50, grader: "PSA", search: "charizard", maxPrice: 1500) {
    totalCount generatedAt
    pageInfo { hasNextPage endCursor }
    edges { node { cert grader grade name year set number game language price frontImage backImage } }
  }
}
  • game, grader and grade match exactly, ignoring case.
  • search matches the name, set, card number or cert.
  • minPrice and maxPrice are in USD.
  • Page with after: endCursor, up to 250 per page.

The list is live, at most 30 seconds old (see generatedAt). A slab drops off as soon as anyone orders or requests it. slab(cert) reads one slab and returns null once it is gone.

Order slabs to ship

Put slabs on a createOrder as lines with a cert, on their own or alongside other products. Needs slabs:write. Works with either key type.

mutation {
  createOrder(input: {
    lines: [{ cert: "12345678", quantity: 1 }, { sku: "PKMS-1465-N", quantity: 1 }],
    shippingAddress: { firstName: "Sam", lastName: "Lee", address1: "1 Main St", city: "Dallas",
                       province: "TX", country: "US", zip: "75001" }
    reference: "PO-1045", idempotencyKey: "PO-1045-order" }) {
    hold { id status lines { cert sku title unitPrice } subtotal shipping tax total }
    problems { code message cert sku }
  }
}
  • Slabs go on the same order at their list price and ship with everything else, under the usual payment and shipping terms.
  • All or nothing: if any slab is no longer available, nothing is ordered, and the problem names its cert (NOT_AVAILABLE).
  • dryRun: true prices slabs from the list without setting anything aside.
  • If the vault is briefly unreachable you get an UNAVAILABLE error. Retry with the same idempotencyKey.

Buy to keep in the vault vaulting keys

requestSlabs buys slabs that stay in TCW's vault as yours, with no tax and no shipping. Needs a vaulting key with slabs:write.

mutation {
  requestSlabs(input: { certs: ["81234567", "81234568"], reference: "PO-2201", idempotencyKey: "PO-2201-slabs" }) {
    request { id status units total lines { cert grader grade name price } unavailable { cert reason } }
    problems { code message cert }
  }
}
  • The certs are set aside straight away and their prices are locked. If prices refreshed since you browsed, the locked price can differ slightly; the request shows the exact amount.
  • Unlike orders, this is not all or nothing: certs that have gone come back in unavailable (and as NOT_AVAILABLE problems), and the rest are still requested.
  • Each day we total your slab requests and invoice you. To have vaulted slabs shipped later, email us.
statusmeans
REQUESTEDSet aside for you at the locked prices, waiting for payment.
PAIDPaid and being recorded, usually within minutes.
OWNEDYours. TCW keeps storing them.
CANCELLEDWithdrawn by TCW before payment, for example at your request. The slabs went back on offer.
REJECTEDNone of the certs were available. Nothing to pay.

Read them back with slabRequest(id) and slabRequests(status, first). A request takes up to 50 certs, each at most once (DUPLICATE_CERT).

Reference

Problem codes

Business-rule failures come back in problems with HTTP 200, not as GraphQL errors. We understood the request but didn't carry it out, and nothing was written.

codemeaning
SKU_NOT_FOUNDNo live product with that SKU or variantId, or a line named none or more than one of sku, variantId and cert.
NOT_AVAILABLEThe item or slab isn't for sale (or a slab was put on a hold).
INSUFFICIENT_STOCKFewer units available than you asked for; the message says how many.
INVALID_QUANTITY, DUPLICATE_SKU, DUPLICATE_CERT, NO_LINESMalformed lines.
TOO_MANY_UNITS, VALUE_LIMIT, TOO_MANY_HOLDS, INVALID_DAYSOver a limit.
HOLD_NOT_HELD, HOLD_EXPIREDThe hold isn't in a state that allows this, such as releasing it after requesting shipment.
IDEMPOTENCY_MISMATCHThat idempotencyKey was already used for a different request.
STORE_CREDIT_NOT_SET_UP, INVALID_AMOUNT, CREDIT_LIMITrequestTopUp: no retainer on your account; the amount isn't a positive number with at most 2 decimals; or it would go over your limit.

Limits

limitdefault
Units per order or hold50
Value per order or hold5,000 USD at retail
Open holds (HELD) at once50. Requests waiting for payment don't count.
Hold length1 to 7 days per request, 14 days in total
Certs per slab request50
Requests per minute, per key300, counting errors
Writes per minute, per key20, separate from the request limit

Need more units or open holds? Ask: they are settings on your key and we can raise them.
