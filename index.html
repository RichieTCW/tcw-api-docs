TCW Partner API Guide

A GraphQL API over Trading Card World's live catalog: products, variants, prices, images, and stock, plus holds that reserve stock for you, shipment requests that become orders we ship once you have paid for them, and, for partners set up for it, graded slabs you can buy by cert and keep in TCW's vault. This page is everything you need to integrate.

Connect

endpoint
POST https://tcw-api-8rgfmmib.uc.gateway.dev/graphql
auth
Header x-api-key: <your key> on every request. Your key was issued to you once; TCW does not store it and cannot recover it. If it's lost, ask for a new one.
body
JSON {"query": "...", "variables": {...}}, standard GraphQL over HTTP. GET with a query parameter also works for simple reads.
liveness
GET https://tcw-api-8rgfmmib.uc.gateway.dev/status, no key needed, returns {"ok":true,"version":"..."}
schema
Introspection is enabled. Point any GraphQL client at the endpoint with your key and it will autocomplete.

First call

curl -s https://tcw-api-8rgfmmib.uc.gateway.dev/graphql \
  -H "x-api-key: $TCW_API_KEY" -H "content-type: application/json" \
  -d '{"query":"{ variant(sku:\"PKMS-3246-N\"){ sku price stock{ band quantity checkedAt } product{ title } } }"}'
{"data":{"variant":{"sku":"PKMS-3246-N","price":"300.00",
  "stock":{"band":"IN_STOCK","quantity":4,"checkedAt":"2026-09-10T21:14:02Z"},
  "product":{"title":"Scarlet & Violet: Base Set - Booster Box"}}}}

What you can read

Three entry points, all on Query.

fieldargumentsreturns
productsfirst (max 250), after cursor, query Shopify search syntax, updatedSince ISO datetimeA page of products, newest-updated first, with cursor paging.
productone of id, handle, skuOne product, or null.
variantskuOne variant with its parent product, or null.

Product

id, handle, title, status, productType, vendor, tags, category (Shopify standard taxonomy node, when set), card (clean card details for trading cards: game, setName, setCode, cardNumber, rarity, edition, releaseDate, language, finishes, characters; null for other products), descriptionHtml, images, variants, url, createdAt, updatedAt.

Variant

id, sku, title, barcode, price (USD, string), compareAtPrice, availableForSale, stock, product.

Stock

fieldmeaning
quantityExact on-hand count from the shop's inventory. Your key includes the inventory:read scope, so this is always populated. It can go negative when the shop has oversold an item; treat anything at or below zero as none available.
bandA convenience summary of the same number: IN_STOCK more than 3, LOW 1 to 3, OUT zero or less. Use quantity for anything that matters.
checkedAtWhen this figure was read from the shop's inventory system, i.e. the moment of your request.
A stock figure is not a reservation. TCW sells in a physical store and online at the same time, and quantity is what is available right now with every existing hold and unshipped order already taken out. It can be gone a minute later. If you need units kept for you, place a hold: that is the only thing that takes stock off the shelf.

Inventory lookups

Every example below was run against the live API. Stock always comes from the variant, because each condition or packaging of an item is its own variant with its own count.

One SKU

{ variant(sku: "PKMS-3246-N") { sku price availableForSale stock { quantity checkedAt } } }
{"data":{"variant":{"sku":"PKMS-3246-N","price":"300.00","availableForSale":true,
  "stock":{"quantity":4,"checkedAt":"2026-09-10T15:52:17Z"}}}}

The same, with a variable

{"query": "query Stock($sku: String!) { variant(sku: $sku) { sku stock { quantity } } }",
 "variables": {"sku": "PKMS-3248-N"}}

Several SKUs in one request

Use aliases, up to 10 per request. Each alias is one Shopify lookup on our side, so this is the efficient way to check a short list.

{
  a: variant(sku: "PKMS-3246-N") { sku stock { quantity } }
  b: variant(sku: "PKMS-3311-N") { sku stock { quantity } }
  c: variant(sku: "PKMS-3248-N") { sku stock { quantity } }
}
{"data":{"a":{"sku":"PKMS-3246-N","stock":{"quantity":4}},
         "b":{"sku":"PKMS-3311-N","stock":{"quantity":1}},
         "c":{"sku":"PKMS-3248-N","stock":{"quantity":80}}}}

Every condition of one card

Fetch the product and read all its variants. Singles carry one variant per condition tier.

{ product(handle: "espeon-deoxys-gx-sm240-sun-moon-black-star-promos") {
    title
    variants { sku title price stock { quantity } } } }
"variants":[{"sku":"SMP-SM240-EN-HF-1","title":"Near Mint Holofoil","stock":{"quantity":0}},
            {"sku":"SMP-SM240-EN-HF-2","title":"Lightly Played Holofoil","stock":{"quantity":0}},
            {"sku":"SMP-SM240-EN-HF-3","title":"Moderately Played Holofoil","stock":{"quantity":1}}, ...]

The same works with product(sku: "SMP-SM240-EN-HF-3"): pass any one variant's SKU and you get the whole product with all of its variants.

By barcode (UPC)

{ products(first: 1, query: "barcode:820650853463") {
    edges { node { title variants { sku barcode stock { quantity } } } } } }

A SKU family by prefix

{ products(first: 250, query: "sku:PKMS-32*") {
    pageInfo { hasNextPage endCursor }
    edges { node { title variants { sku stock { quantity } } } } } }

Only what is in stock

{ products(first: 250, query: "inventory_total:>0 AND product_type:'Pokemon Sealed'") {
    pageInfo { hasNextPage endCursor }
    edges { node { title variants { sku price stock { quantity } } } } } }

inventory_total is the sum across a product's variants, so a product with one in-stock condition and four sold-out ones still matches; check each variant's quantity.

Common patterns

Page through the catalog

query Page($after: String) {
  products(first: 250, after: $after) {
    pageInfo { hasNextPage endCursor }
    edges { node { id handle title productType tags
      variants { sku price compareAtPrice availableForSale stock { band quantity } } } }
  }
}

Loop while hasNextPage, passing endCursor as after. The live catalog is a few thousand products, so a full pull is about 14 requests at 250 per page.

Keep in sync without re-pulling everything

{ products(first: 250, updatedSince: "2026-09-11T00:00:00Z") {
    pageInfo { hasNextPage endCursor }
    edges { node { id updatedAt variants { sku price stock { band quantity } } } } } }

Poll with the timestamp of your last successful sync. Products are ordered newest-updated first, so the first page is the most recent changes.

Filter with Shopify search syntax

{ products(first: 50, query: "product_type:'Pokemon Sealed'") { edges { node { title } } } }
{ products(first: 50, query: "tag:'Prismatic Evolutions'") { edges { node { title } } } }
{ products(first: 50, query: "title:Charizard*") { edges { node { title } } } }

The query argument accepts Shopify's product search syntax: product_type:, tag:, vendor:, title:, sku:, with AND, OR, - for not, and * as a trailing wildcard. Field matches are exact terms, so use the wildcard for partial titles. Regardless of what you pass, results are always limited to live, published products.

Look up one SKU

{ variant(sku: "SV05-007-EN-NH-1") { price availableForSale stock { band quantity } product { title handle url } } }

Single cards carry one SKU per condition. The suffix encodes it: -NH-1 is Near Mint Holo, -HF-1 is Holofoil, and the trailing number is the condition tier. Each condition is its own variant with its own price and stock.

Holds and orders

A hold reserves specific units for you for a set number of days. While it stands, those units are unavailable to every other channel, including TCW's own store and website. At the end you either convert it into a shipment request, release it, or let it expire, at which point the units go back on sale. createOrder does the hold and the shipment request in one call.

Orders are paid first. A shipment request is not yet an order. Each day we total your requests (items at hold prices, plus $9.99 shipping per shipment, plus tax) and invoice you. Once that invoice is paid, each request becomes an order and we ship it. Nothing ships, and no order exists, before payment.

Life of a hold

statusmeanswhat moves it on
HELDUnits reserved for you until expiresAt.You call convertHold, extendHold or releaseHold, or it expires.
REQUESTEDYou asked for it to ship. Still reserved; shipping, tax and total are set. Waiting for payment.We receive payment for that day's invoice.
PAIDPayment received; the order is being created.Automatic, within about 15 minutes.
CONVERTEDAn order exists. Read it from the hold's order.We ship it; follow order.fulfillmentStatus.
RELEASED / EXPIREDUnits back on sale.Final.

A line names its item by sku or by variantId, the Variant.id the catalog returns. Use variantId for the products that have no SKU; it is TCW's own id and never changes. These need the holds:write and orders:write scopes on your key; orders:read lets you read your own holds and orders back. You only ever see and control your own. Prices are TCW's retail prices at the moment the hold is placed.

mutationdoes
createHold(input)Reserve units for holdDays (default 3, max 7).
extendHold(id, days)Push the expiry out. A hold can last 14 days in total.
releaseHold(id)Give the units back. Safe to repeat.
convertHold(id, input)Request that the hold ship to an address you give. It becomes an order once you have paid for it.
createOrder(input)Hold and request the shipment in one call, when you don't need time to decide. Same rules, limits and payment as convertHold.

Queries: hold(id), holds(status, first), order(id), orders(first).

Every write has a dry run

Pass dryRun: true to createHold or createOrder and you get the priced lines and any problems, and nothing is written. Do this first; the real call takes the identical input. A dry run prices the items only: shipping and tax are added when the shipment request is recorded.

mutation {
  createHold(input: { lines: [{ sku: "PKMS-1465-N", quantity: 1 }], holdDays: 1,
                      reference: "PO-1042", idempotencyKey: "PO-1042-hold", dryRun: true }) {
    hold { status units subtotal expiresAt lines { sku title unitPrice } }
    problems { code message sku }
  }
}
{"data":{"createHold":{"hold":{"status":"PREVIEW","units":1,"subtotal":"80.00",
  "expiresAt":"2026-09-19T16:25:45Z",
  "lines":[{"sku":"PKMS-1465-N","title":"Scarlet & Violet: Destined Rivals - Booster Bundle","unitPrice":"80.00"}]},
  "problems":[]}}}

Place the hold

Same input without dryRun. Keep the returned id; it is how you refer to the hold from now on.

{"data":{"createHold":{"hold":{"id":"h_d79c13c62082","status":"HELD","units":1,"subtotal":"80.00",
  "currency":"USD","expiresAt":"2026-09-19T16:25:45Z","createdAt":"2026-09-18T16:25:45Z"},"problems":[]}}}

From this moment the variant's stock.quantity is one lower for everyone, including you.

A product with no SKU

Some products, mostly sports boxes and older sealed items, have no SKU. Their Variant.sku is empty, but every variant has an id. Pass that instead:

mutation {
  createHold(input: { lines: [{ variantId: "44123456789012", quantity: 1 }, { sku: "PKMS-1465-N", quantity: 2 }],
                      idempotencyKey: "PO-1043-hold", dryRun: true }) {
    hold { lines { sku variantId title quantity unitPrice } subtotal }
    problems { code message sku variantId }
  }
}

Both kinds of line can be mixed in one request. Every hold and order line comes back with both sku and variantId, so you can match on whichever you keep.

idempotencyKey: so a retry can never double an order

Networks fail at the worst moment. Your system sends "hold one bundle", we create the hold, and the reply is lost on the way back to you, or your client gives up waiting. From your side the request failed, so it retries. Without protection that retry creates a second hold, and on createOrder a second shipment request that you would be invoiced for.

The idempotencyKey prevents that. It is a label you make up that means "this particular request", and it is required on createHold and createOrder. Use something you already have, such as your purchase order number with a suffix: PO-1042-hold. We remember which key created which hold.

  • Same key, same input: we do nothing new and return the hold that key created the first time. Your retry is harmless. Send the identical request as many times as you like.
  • Same key, different input (say the quantity changed): we cannot tell a retry from a new request that reused a key, so we refuse with IDEMPOTENCY_MISMATCH and write nothing. Use a fresh key for the new request.
  • New key: a new hold.

Keys are scoped to you, so they only need to be unique within your own system. The rule of thumb: generate the key before you send, store it with the request, and reuse it on every retry of that request. convertHold, extendHold and releaseHold don't need one because they act on a hold that already exists; repeating them is safe by nature.

Request the shipment

convertHold records that you want the hold shipped. It does not place the order yet: the hold moves to REQUESTED and its units stay reserved for you while payment is pending (expiresAt shows until when). We add a flat $9.99 shipping charge to each hold you convert, and tax on the items and shipping (none if your account is tax exempt); the hold's shipping, tax and total show exactly what you will be invoiced for it.

Ship to your customer. shippingAddress can be any address: yours, or your own customer's for drop shipping. It takes firstName, lastName, company, address1, address2, city, province, country, zip and phone; address1, city, country and zip are required. email is optional and goes on the order. reference is yours (a PO or your customer's order number) and is echoed back on the hold and the order. The address cannot be changed through the API after the request, so check it first.

mutation {
  convertHold(id: "h_d79c13c62082", input: {
    shippingAddress: { company: "Acme Cards", firstName: "Receiving", lastName: "Dept",
                       address1: "20 W 34th St", city: "New York", province: "NY", country: "US", zip: "10001" }
    reference: "PO-1042" }) {
    hold { status subtotal shipping tax total expiresAt }
    order { name }
    problems { code message }
  }
}
{"data":{"convertHold":{"hold":{"status":"REQUESTED","subtotal":"80.00","shipping":"9.99","tax":"7.99","total":"97.98",
  "expiresAt":"2026-09-25T16:28:40Z"},
  "order":null,"problems":[]}}}

Calling it again is safe and returns the hold as it stands. A requested hold can no longer be extended or released from the API; contact us if you need to cancel one. Pay before expiresAt: after that the reservation lapses and the units can sell elsewhere. After payment, read the order from the hold:

{ hold(id: "h_d79c13c62082") { status order { id name paymentStatus fulfillmentStatus subtotal shipping tax total } } }
{"data":{"hold":{"status":"CONVERTED","order":{"id":"7087128739978","name":"#88664","paymentStatus":"PAID",
  "fulfillmentStatus":"UNFULFILLED","subtotal":"80.00","shipping":"9.99","tax":"7.99","total":"97.98"}}}}

Order in one call

createOrder takes the lines and the shipping details together and returns a REQUESTED hold, exactly as if you had called createHold and then convertHold. Keep its id; the order appears on it after payment.

mutation {
  createOrder(input: { lines: [{ sku: "PKMS-1465-N", quantity: 1 }],
    shippingAddress: { firstName: "Sam", lastName: "Lee", address1: "1 Main St", city: "Dallas",
                       province: "TX", country: "US", zip: "75001" }
    reference: "PO-1044", idempotencyKey: "PO-1044-order" }) {
    hold { id status subtotal shipping tax total }
    order { name }
    problems { code message sku }
  }
}
{"data":{"createOrder":{"hold":{"id":"h_5b0e2a9c41f7","status":"REQUESTED","subtotal":"80.00",
  "shipping":"9.99","tax":"7.99","total":"97.98"},"order":null,"problems":[]}}}
How payment works. Requests are totalled per calendar day (US Eastern time): items at hold prices, plus $9.99 shipping per hold, plus tax. An order is only created after that day's invoice is paid, so every order you see has been paid for. To see what is waiting for payment, list holds(status: REQUESTED); the sum of their total for a day is that day's invoice.

Watch it ship

{ order(id: "7087128739978") { name fulfillmentStatus tracking { number url company } } }

fulfillmentStatus moves from UNFULFILLED to FULFILLED and tracking fills in when we ship. Polling every few minutes is fine.

Release, list, and let expire

mutation { releaseHold(id: "h_d79c13c62082") { hold { status } problems { code message } } }
{ holds(status: HELD) { id units subtotal expiresAt reference } }
{ holds(status: REQUESTED) { id total expiresAt reference } }
{ orders(first: 20) { name createdAt total fulfillmentStatus reference } }

A hold you do nothing with expires at expiresAt and the units return to stock. Its status becomes EXPIRED; place a new hold or order if you still want them. holds includes the ones createOrder made; orders lists only paid orders.

Problems

Business rules come back in problems with a 200, not as GraphQL errors. The request was understood but not performed; nothing was written.

codemeaning
SKU_NOT_FOUND / NOT_AVAILABLENo live product with that SKU or variantId (or a line gave neither, or both), or it is not for sale.
INSUFFICIENT_STOCKFewer units available than requested; the message says how many.
INVALID_QUANTITY / DUPLICATE_SKU / NO_LINESMalformed lines.
TOO_MANY_UNITS / VALUE_LIMIT / TOO_MANY_HOLDS / INVALID_DAYSOver a limit, see below.
HOLD_NOT_HELD / HOLD_EXPIREDThe hold is not in a state that allows this; e.g. releasing a hold after requesting its shipment.
IDEMPOTENCY_MISMATCHThat key was already used for a different request.

Limits

  • Per hold or order: at most 50 units and 5,000 USD at retail.
  • At most 50 open holds (HELD) at a time. Release or convert one to place another; requested holds waiting for payment don't count.
  • Hold length 1 to 7 days per request, 14 days total after extensions.
  • Writes are limited to 20 per minute per key, separate from the read limit.

Need more room on the unit or open-hold limits? Ask; they are settings on your key and we can raise them for you.

Graded slabs

If your key has the slabs:read and slabs:write scopes, you can browse and buy graded slabs from TCW's vault. Every slab is one of a kind, so it is named by its cert number. The list is live (at most 30 seconds old, see generatedAt), and a slab you or anyone else has requested drops off it.

{
  slabs(first: 50, grader: "PSA", search: "charizard", maxPrice: 1500) {
    totalCount generatedAt
    pageInfo { hasNextPage endCursor }
    edges { node { cert grader grade name year set number game language price frontImage backImage } }
  }
}

Filters game, grader and grade match exactly (any case); search matches the name, set, card number or cert; minPrice / maxPrice are in USD. Page with after: endCursor, up to 250 per page. slab(cert) reads one slab and returns null once it is no longer available.

Request slabs

requestSlabs sets the certs you name aside for you straight away, at their current price, which is then locked on your request. If a price refreshed between your browse and your request, the locked price can differ a little from the list; the request shows the exact amount. Any cert that has gone in the meantime comes back in unavailable and in problems as NOT_AVAILABLE, and the rest are still requested. dryRun: true prices the certs from the list without setting anything aside, and idempotencyKey works exactly as it does for holds.

mutation {
  requestSlabs(input: { certs: ["81234567", "81234568"], reference: "PO-2201", idempotencyKey: "PO-2201-slabs" }) {
    request { id status units total lines { cert grader grade name price } unavailable { cert reason } }
    problems { code message cert }
  }
}

Payment is direct, with no tax and no shipping. Each day we total your slab requests and invoice you. When that invoice is paid, the request moves to PAID and then OWNED. Your slabs stay in TCW's vault after that; to have some shipped, email us.

statusmeans
REQUESTEDSet aside for you at the locked prices, waiting for payment.
PAIDPayment received; being recorded. Usually minutes.
OWNEDYours. TCW keeps storing them.
CANCELLEDWithdrawn by TCW before payment (for example at your request); the slabs went back on offer.
REJECTEDNone of the certs were available. Nothing to pay.

Read them back with slabRequest(id) and slabRequests(status, first). A request takes at most 50 certs (the same unit limit as holds; we can raise it), counts against the 20 writes per minute, and a cert may appear only once (DUPLICATE_CERT). If the slab vault is briefly unreachable, requestSlabs returns an UNAVAILABLE error: retry with the same idempotencyKey.

Limits and errors

statusmeaningwhat to do
401No key sent, or the key isn't recognisedCheck the x-api-key header.
400 "API key not valid" or "expired"Key revoked or expiredContact TCW for a new key.
429Over your per-minute rate limitBack off for the retry-after seconds, then resume. A few requests per second stays well within it.
200 with errorsQuery problem: unknown field, too deep, too expensiveRead the message; it names the field or limit.
  • Rate limit is per key: 300 requests per minute unless you were told otherwise. Every request counts, including errors. Paging at a few requests per second is fine.
  • Query limits: depth 7, at most 10 aliases, and a cost budget sized so a full first: 250 page with every product and variant field fits. Larger pages are refused; page instead.
  • No batching of multiple operations in one request.
  • Scope errors come back as a GraphQL error with extensions.code: "FORBIDDEN" naming the scope your key lacks.
